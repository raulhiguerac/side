# Revisión de analytics-service

Revisión de solo lectura del AVM (avalúo automático): endpoint online `/v1/predict`, worker Kafka de predicción batch (`listing-created` → `price-predicted`), adapters de MLflow/DB y schemas de validación. Se revisó por rebanadas verticales (ruta → caso de uso → adapters → schema) cotejando contra `domain-invariants.md` (invariantes transversales, analytics no tiene sección propia) y los riesgos de `backend.md`.

## Resumen

- **Hallazgo principal:** el flujo async por Kafka **no es idempotente** y combina commit de offset *at-least-once* con publicación de eventos y persistencia sin clave de deduplicación. Un reproceso del batch (crash o fallo de entrega parcial) genera **filas de predicción duplicadas en DB y eventos `price-predicted` duplicados** aguas abajo. Son dos bugs que se refuerzan (Bug·alta).
- La suite de tests **no corre** en el entorno de auditoría (`pytest` no está instalado en el venv del servicio): no hay señal de verde/rojo. Los tests unitarios existen y son razonablemente completos, pero `tests/integration/**` está **vacío** (solo `__init__.py`), así que ninguna rebanada se ejercita extremo a extremo. (Mejoras de proceso.)
- El resto de la rebanada online (`/predict` → `OnlinePrediction` → DB) respeta los invariantes de sync/async, rollback y traducción de error. Ver "Revisado sin hallazgos".

## Bugs

### [Bug · alta] El consumidor Kafka no es idempotente: reproceso duplica predicciones en DB
- **Dónde:** `src/app/services/prediction/adapters/sql_prediction_repository.py:14-18` (`batch_add`) junto con `src/app/models/prediction.py:55` (PK `id`) y `src/app/workers/listing_created/consumer.py:170-210` (`consume_batch`).
- **Escenario:** llega un mensaje de `listing-created` para `property_id=P`. El worker predice, inserta la fila y publica a `price-predicted`, pero el proceso muere (o un `_emit` posterior lanza `WorkerDeliveryError`) **antes** de `self.consumer.commit()` (línea final de `consume_batch`). Como `enable.auto.commit=False` y el offset no se confirmó, Kafka reentrega el mismo mensaje. El segundo pase vuelve a predecir e inserta **otra** fila para `P`. Resultado: dos (o más) predicciones para el mismo listing; esperado: una sola, o re-escritura idempotente.
- **Por qué pasa:** `batch_add` hace `insert(...).on_conflict_do_nothing()`, pero el único constraint de la tabla es la PK `id`, que es un `uuid4` nuevo en cada `build_prediction_record` (`record_builder.py:16`). Nunca hay conflicto, así que `on_conflict_do_nothing` no deduplica nada: cada reintento crea una fila con `id` distinto. No existe constraint único sobre `property_id` (ni sobre `property_id + model_version`), y en el camino row-by-row (`batch.py:60-70`) pasa lo mismo.
- **Propuesta:** definir la clave de idempotencia del dominio (lo más probable: `property_id` para el flujo batch, o `property_id + model_version`) y materializarla como constraint único + `index_elements` en el `on_conflict`. Si se quiere "última predicción gana", usar `on_conflict_do_update`. Si `property_id` puede ser `NULL` (online), excluir esas filas del índice único (índice parcial `WHERE property_id IS NOT NULL`). El invariante transversal de "escritura idempotente por id determinístico" ya existe en properties (`adr-bulk-idempotent-external-id`); acá falta el equivalente.
- **Test sugerido:** test de integración con DB real: consumir el mismo `WorkerMessage` dos veces y afirmar `count(*)` de `predictions` para ese `property_id` == 1. A nivel unit, afirmar que `batch_add` pasa `index_elements`/constraint al `on_conflict`.
- **Confianza:** alta

### [Bug · alta] `price-predicted` se publica antes de confirmar el offset: eventos duplicados en reproceso
- **Dónde:** `src/app/workers/listing_created/consumer.py:181-210` (orden `_emit(predictions)` → `_emit(retry)` → `_emit(dlq)` → `self.consumer.commit()`).
- **Escenario:** el batch produce N predicciones. `_emit(topic_predictions, ...)` entrega los eventos a `price-predicted` con éxito, pero luego `_emit(topic, retry_messages)` o `_emit(topic_dlq, dlq)` lanza `WorkerDeliveryError` (línea `consumer.py:95`), o el proceso cae entre el emit y el commit. Como el offset no se confirma, el batch completo se reprocesa y `price-predicted` recibe **otra vez** los mismos eventos. El consumidor de properties (`SetEstimatedPriceUseCase`, hoy no cableado — ver `open-items.md`) recibiría precios duplicados. Esperado: cada predicción se publica una sola vez, o el downstream es idempotente.
- **Por qué pasa:** patrón at-least-once (correcto para no perder trabajo) sin deduplicación aguas abajo ni "outbox": publicar y luego commitear el offset implica que cualquier fallo entre medio reproduce todo. Se agrava con el bug anterior (la DB tampoco deduplica), así que no hay ninguna barrera contra duplicados en toda la cadena.
- **Propuesta:** aceptar at-least-once pero hacer idempotente lo observable: (a) clave determinística en DB (bug anterior) para que la re-persistencia sea no-op; (b) que el evento `price-predicted` lleve una clave idempotente (`property_id` + `model_version`) para que el consumer de properties deduplique, o (c) commitear el offset solo después de confirmar la entrega de **todos** los emits (ya casi está, pero un fallo en retry/dlq revierte también los `price-predicted` ya entregados → duplicados). Documentar explícitamente la garantía elegida.
- **Test sugerido:** test que simule `WorkerDeliveryError` en el `_emit` de retry después de un `_emit(predictions)` exitoso y afirme que, al reprocesar, el downstream no ve el evento dos veces (requiere la clave idempotente del evento).
- **Confianza:** alta

### [Bug · media] Fallo de MLflow/DB a mitad de batch descarta el batch entero sin DLQ
- **Dónde:** `src/app/workers/listing_created/consumer.py:181` (`result = await self.uc.execute(...)`) y `src/app/services/prediction/use_cases/batch.py:30-33` (`model.batch_predict`).
- **Escenario:** el batch trae 50 mensajes válidos. MLflow está caído o devuelve timeout → `self.model.batch_predict` lanza dentro de `uc.execute`. La excepción se propaga fuera de `consume_batch` (no hay `try/except` alrededor de `uc.execute`), sube hasta `runner.py:run`, se loguea como `worker_fatal_error` y **mata el worker**. El offset no se confirma (bien, no se pierden), pero: (a) los `rejected_messages`/DLQ ya calculados en este ciclo se pierden; (b) el worker queda caído hasta reinicio; (c) un único mensaje "veneno" que haga fallar `batch_predict` o `batch_add` repetidamente bloquea todo el topic (el contador `attempts>3` → DLQ solo aplica a fallos de parseo/validación, no a fallos del modelo/DB, que nunca incrementan `attempts`).
- **Por qué pasa:** el manejo de errores del batch distingue parseo (→ DLQ) de persistencia (→ fallback row-by-row → `failed` → retry), pero un fallo del **modelo** (`batch_predict`) no está contemplado: revienta antes de construir `db_records`. No hay reintento con backoff ni corte de circuito para MLflow.
- **Propuesta:** envolver `uc.execute` (o la llamada al modelo) para distinguir "infra temporalmente caída" (reintentar el ciclo, no matar el worker) de "mensaje veneno" (a DLQ tras N intentos). Como mínimo, no perder los `dlq` ya acumulados cuando el modelo falla.
- **Test sugerido:** `uc.execute` lanza `Exception` → afirmar que el offset NO se commitea y que el worker no muere en el ciclo (que reintente), y que los mensajes rejected acumulados igual se emiten.
- **Confianza:** media

### [Bug · media] El reintento (`attempts`) nunca crece ante fallos de persistencia → re-encolado infinito posible
- **Dónde:** `src/app/workers/listing_created/consumer.py:191-207` (construcción de `retry_messages`) y `batch.py:55-76` (camino `failed`).
- **Escenario:** un mensaje con `attempts=1` falla la inserción row-by-row (constraint, deadlock, etc.) → vuelve en `result.failed` → se re-emite a `listing-created` con `attempts+1=2`. Correcto hasta acá. Pero si el fallo es **determinístico** (ej. un dato que siempre viola un constraint), el mensaje escala 2→3→4 y recién en `attempts>3` va a DLQ (`consumer.py:150`). El tope existe, bien. El problema es el caso inverso: cuando `batch_add` (bulk) falla y el fallback row-by-row **sí** inserta, el mensaje se considera `prediction` y nunca se cuenta; pero si el `_emit` de retry falla (ver Bug·alta de offsets), al reprocesar el `attempts` del envelope original **no cambió** (sigue en el valor que traía Kafka), así que no hay convergencia hacia la DLQ a través de reprocesos de offset — solo a través de re-emisiones explícitas.
- **Por qué pasa:** hay dos mecanismos de reintento solapados y no coordinados: el re-encolado explícito con `attempts+1` (incrementa, converge a DLQ) y el reproceso implícito por offset no confirmado (no incrementa `attempts`, no converge). Un fallo determinístico de entrega mantiene el batch en el segundo mecanismo indefinidamente.
- **Propuesta:** unificar la semántica de reintento. Si se confía en el re-encolado explícito, confirmar el offset del batch original siempre que los mensajes problemáticos ya estén re-emitidos o en DLQ (como hoy intenta), y asegurar que el emit de retry/DLQ sea atómico respecto del commit (resolver el Bug·alta de offsets). Documentar la garantía.
- **Test sugerido:** simular fallo de entrega del retry y afirmar que no se entra en un ciclo donde `attempts` nunca avanza.
- **Confianza:** media

## Mejoras

### [Mejora · alta] La suite de tests no corre en el entorno de auditoría (sin señal de tests)
- **Dónde:** `audit-report.txt`, sección `analytics-service: pytest (unit)` → `error: Failed to spawn: pytest - No such file or directory`.
- **Beneficio/riesgo que elimina:** hoy `make audit` **no ejecuta ni un test** de analytics (el venv del servicio no tiene `pytest` instalado), así que el verde del pipeline no cubre este servicio. Cualquier regresión en las rebanadas pasa inadvertida. Instalar `pytest` (y plugins: `pytest-asyncio`, visto en los `@pytest.mark.asyncio`) en el entorno de auditoría o declararlo como dependencia de dev del servicio restaura la señal. Es hallazgo de proceso, no de código.
- **Confianza:** alta

### [Mejora · alta] `tests/integration/**` está vacío: ninguna rebanada se ejercita extremo a extremo
- **Dónde:** `tests/integration/adapters/`, `tests/integration/api/`, `tests/integration/services/`, `tests/integration/performance/` (todos contienen solo `__init__.py`).
- **Beneficio/riesgo que elimina:** los unit tests mockean `run_in_threadpool`, la UoW y el modelo, así que los bugs de idempotencia y de orden commit/offset (ver Bugs) son **justo** los que un unit test no puede atrapar: requieren DB real (constraint único, `on_conflict`) y un Producer/Consumer real o fake con offsets. Agregar integración para: (a) `/v1/predict` contra DB real (persistencia + 201), (b) el consumer con DB real afirmando idempotencia, (c) adapter de MLflow contra un model stub. El scope del review pedía "tests de integración que de verdad ejercitan el flujo"; hoy no existen.
- **Confianza:** alta

### [Mejora · media] `ModelClient` lee la versión del alias en cada predicción, desacoplada del modelo cargado al init
- **Dónde:** `src/app/integrations/ml/mlflow/model.py:24-37` (`__init__` carga `MLFLOW_MODEL_URI` una vez; `get_version` consulta el alias `production` en cada request) y `avm_model_adapter.py:12,17`.
- **Beneficio/riesgo que elimina:** el modelo se carga una vez al construir `ModelClient` desde `MLFLOW_MODEL_URI`, pero `get_version(model_name="bogota-avm", alias="production")` consulta el registry **en cada** predicción. Si `MLFLOW_MODEL_URI` no apunta exactamente al alias `production`, o si se promueve una versión nueva al alias mientras el proceso vive, el `model_version` reportado/persistido puede **no corresponder** al modelo que realmente hizo la inferencia (el cargado en memoria). Además es una llamada de red por predicción (latencia + dependencia dura de MLflow en el path online). Propuesta: resolver versión y cargar modelo de forma consistente (misma fuente) y cachear la versión junto al modelo; refrescar explícitamente al rotar.
- **Confianza:** media

### [Mejora · media] Settings de infra (MLflow, Kafka, S3) viven en `os.getenv` disperso, no en `settings`
- **Dónde:** `src/app/core/config/settings.py` (solo DB/Redis/Keycloak) vs. `integrations/ml/mlflow/model.py:12-22` y `workers/listing_created/consumer.py:18-26` (`os.getenv` directo de `MLFLOW_*`, `AWS_*`, `KAFKA_*`, `WORKER_PRINCIPAL`).
- **Beneficio/riesgo que elimina:** `backend.md` marca como riesgo los valores de entorno fijos y la configuración dispersa. Hoy la config de MLflow/Kafka/S3 no pasa por `Settings`, así que no hay validación central, ni defaults documentados, ni un solo lugar donde ver qué necesita el servicio. Centralizar en `Settings` (con tipos y validación de UUID para `WORKER_PRINCIPAL`) reduce errores de arranque y facilita staging/prod. Nota: no se encontró URL hardcodeada en código (todo sale de env), así que no es un bug de valores fijos — es una mejora de organización/validación.
- **Confianza:** media

### [Mejora · baja] Hallazgos ruff que valen un vistazo: F811 (redefinición) y RUF059 (variable desempaquetada sin uso)
- **Dónde:** `audit-report.txt`, `analytics-service: ruff` → `F811 redefined-while-unused (2)`, `RUF059 unused-unpacked-variable (2)` (más 48 hallazgos de ruido: I001, UP045, B008 en `Depends` que `backend.md` marca como no reportar). Son baratos de revisar y a veces delatan un bug latente. Propuesta: correr `ruff check src --select F811,RUF059` en el servicio y resolver los 4 puntualmente.
- **Confianza:** baja

- **Beneficio/riesgo que elimina:** mismo patrón que `open-items.md` reporta para catalog/properties ("Orígenes CORS fijos en código"). Para staging/prod el origen debe venir de configuración. Es deuda conocida cross-service; se anota para consistencia, no como bug nuevo.

## Convención

### [Convención · baja] `handlers` solo registra `BaseError`; el 422 de validación depende del default de FastAPI
- **Dónde:** `src/app/api/handlers/exception_handlers.py:17-45` (solo `@app.exception_handler(BaseError)`).
- **Regla:** `backend.md` espera que la validación del input se rechace como 422 **antes** del caso de uso. En `/predict`, `PredictionRequest` (`StrictBase`, `extra="forbid"`, campos con `ge/le`) sí produce 422 vía el `RequestValidationError` por defecto de FastAPI, así que el comportamiento es correcto. La observación es que ese 422 no está cubierto por un handler propio (formato de error distinto al `{message, code, context}` de `BaseError`): el front recibe dos formas de error según el tipo. Propuesta menor: registrar un handler de `RequestValidationError` que normalice el shape, por consistencia. No es bug: la validación ocurre y corta antes del UC.
- **Confianza:** baja

## Revisado sin hallazgos

- **Rebanada online `/v1/predict` → `OnlinePrediction` → DB.** `predict.py` delega en el UC pasando `principal.sub` (identidad del JWT, el UC no lee el token — cumple invariante). `OnlinePrediction.execute` usa `await run_in_threadpool(partial(...))` tanto para el modelo como para el repo (cumple el invariante sync/async con `partial`), hace `commit()` y, ante fallo, `rollback()` + envuelve en `PredictionPersistenceError` (cumple rollback tras fallo de escritura). Cubierto por `test_online_prediction.py` (happy path, rollback, wrap de causa, log, exclusión de `property_id` al modelo).
- **Validación del input de predicción (`PredictionRequest`, schemas/prediction.py).** `StrictBase` con `extra="forbid"` + rangos (`area_m2 gt 0 le 2000`, `stratum 1..6`, `bedrooms/bathrooms/parking 0..20`, `year_built 1900..2100` nullable, lat/lon acotados). Rechaza features faltantes/erróneas con 422 antes del UC. El `exclude={'property_id'}` al llamar al modelo evita filtrar un campo que el modelo no espera.
- **Carga del modelo desde el MLflow registry (no S3 directo).** `AVMModelAdapter`/`ModelClient` resuelven vía `mlflow.pyfunc.load_model(MLFLOW_MODEL_URI)` y `MlflowClient.get_model_version_by_alias`; S3 (SeaweedFS) solo entra como backend de artefactos de MLflow (`MLFLOW_S3_ENDPOINT_URL`), no como carga directa. (La consistencia versión↔modelo se anota como Mejora·media aparte.)
- **UoW y repo síncrono.** `SqlPredictionUnitOfWork` envuelve `session.commit/rollback/refresh/begin_nested` en `run_in_threadpool` (correcto); `SqlPredictionRepository.add/batch_add` son síncronos y se invocan con `partial`. El fallback row-by-row usa savepoints (`begin_nested`/`rollback_to_savepoint`) para no perder las filas sanas cuando el bulk falla — bien diseñado y cubierto por `test_batch_prediction.py`.
- **Parseo/validación y DLQ del worker (camino de datos).** `_poll_batch` separa mensajes no-UTF8 a DLQ con el payload en base64 (trazable); `consume_batch` manda JSON inválido, `ValidationError` y `attempts>3` a DLQ. Bien cubierto por `test_consumer.py` (poll, produce, serialize, consume_batch). El tope `attempts>3` evita el re-encolado infinito del camino de parseo. (Las lagunas están en idempotencia y orden commit/offset, reportadas como Bugs.)
- **Auth / rutas admin.** No hay rutas `/admin` en el servicio (`api/main.py` solo monta `health` y `predict`), así que el invariante `require_admin` no aplica. `get_current_principal` deriva identidad del JWT de Keycloak (JWKS), traduce fallos a `UnauthorizedError` (401) y maneja `DecodeError` explícitamente — nota: aquí sí atrapa `DecodeError`, a diferencia del gap que `open-items.md` reporta para catalog/users; no se encontró el bug del 401-por-token-malformado en analytics.
- **Degradación de cache.** El scaffolding de Redis existe (`integrations/cache/redis/`) pero las rebanadas revisadas (predict online y batch) **no usan cache**, así que no hay invalidación ni degradación que revisar en este flujo.

### Nota de alcance

- No se pudo ejecutar `pytest` ni `ruff` en el entorno de auditoría (ninguno instalado para este servicio), así que las afirmaciones sobre tests y las líneas exactas de F811/RUF059 se basan en lectura de código y en `audit-report.txt`, no en ejecución. Los bugs de idempotencia y orden commit/offset se razonaron contra el código fuente; confirmarlos empíricamente requiere los tests de integración que hoy faltan.
- El directorio `services/market/**` está vacío (solo `__init__.py`): no hay rebanada que revisar ahí todavía.
