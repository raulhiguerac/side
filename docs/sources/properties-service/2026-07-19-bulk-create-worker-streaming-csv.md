## Context
Follow-up to the catalog-service H3 precompute/bulk-resolve work (see `2026-07-18-h3-precompute-and-bulk-resolve.md`). This session built the properties-service side: the `BulkCreatePropertiesUseCase` worker needs to read a large CSV from MinIO without loading it fully into memory, batch rows, and resolve lat/lon (catalog) and owner email (users) in bulk instead of N calls per row — plus the HTTP clients/gateways/schemas that connect properties-service to the new catalog and users bulk endpoints.

## Key conclusions
- **`CatalogClient.get_location_info` (singular, GET) was replaced by `get_locations_bulk`** (`POST /v1/geo-resolution/by-coordinates/bulk`, `points: list[dict]`, 30s timeout override on that call only, `self.timeout=2.0` unchanged for `get_neighborhood`). Breaks the old singular caller (`CatalogGateway.get_location_by_point` → `workers/bulk_create_properties.py`'s original per-row `_enrich_location`) intentionally, deferred cleanup.
- **New `UsersClient`** (`integrations/users/users_client.py`) calling `POST /v1/users/resolve` — got its own `UsersClientError`/`error_mapper.py` instead of reusing catalog's (was a copy-paste artifact pointing at the wrong domain). Fixed bugs from the draft: `uuid.UUID` isn't JSON-serializable by `httpx`'s `json=` (needs `str(...)` per id), `tuple(...)` vs `tuple[...]` typo, wrong URL path.
- **Gateway pattern extended, not replaced**: `CatalogGateway`/`UsersGateway` (ports) + `CatalogAdapter`/`UsersAdapter` (adapters) got new bulk methods (`get_locations_bulk`, `resolve_accounts`) alongside the existing singular ones. Local mirror schemas added (`PointToResolve`, `ResolvedPoint` in `catalog_schemas.py`; `ResolvedAccount` in `users_schemas.py`), following the pre-existing `_ExternalSchema(extra="ignore")` convention — properties-service keeps its own copy of the wire contract, no shared package across services.
- **Real bug found and fixed**: `LocationInfo.city_id` had no alias, but catalog-service's wire field is `locality_id` — validation would have failed on every call (old and new). Fixed with `Field(alias="locality_id")`, verified with a live pydantic test; `model_dump()` still outputs `city_id` so downstream code (`row_to_item`) is unaffected.
- **DI wiring**: `get_users_gateway()` added to `api/deps/listing.py` next to `get_catalog_gateway()` (same `@lru_cache` pattern). Not yet wired into `get_bulk_create_properties_uc` (`api/deps/admin.py`).
- **`MinioStorageAdapter.chunk_file`**: user's first draft only yielded once (no loop → silently truncated any file over `chunk_size`) and called blocking boto3 sync calls without `run_in_threadpool` (unlike every other method in that file). Fixed with a `while True` loop + `run_in_threadpool` per `.read()`. Chunk size moved to `settings.STORAGE_CHUNK_SIZE_BYTES` (bumped 1MB → 10MB) instead of a magic number — decoupled from the (still separate, undecided) row-batch-size sent per call to catalog/users bulk endpoints.
- **`workers/helpers/chunking.py::iter_csv_rows`** — the real find of this session: `csv.reader` does **not** raise when fed a buffer cut off mid-quote — it silently truncates the field (verified empirically). `descripcion` fields in the actual seed CSV contain literal embedded newlines spanning multiple physical lines (500 real rows vs 1597 raw `wc -l` lines in `data/ml/AVM/data/seed_bogota_500.csv`), so a naive per-chunk-boundary line split would corrupt data instead of erroring. Fixed by tracking a running count of `"` characters and only handing accumulated text to `csv.reader` once the count is even (no quote left open). Second bug found in the same pass: `str.splitlines()` strips line terminators, so `csv.reader` can't reconstruct multi-line quoted fields correctly even when quote-balanced — needed `splitlines(keepends=True)`. End-to-end validated against the real CSV at 5 chunk sizes (37B to whole-file), byte-identical to `csv.DictReader` read fully in memory.
- **`BulkPropertyCsvRow`** schema added (`admin_schemas.py`) — mirrors the raw CSV header plus a new `email` column (owner resolution, not yet in the actual CSV file). Deliberately keeps messy-value fields (`parqueaderos`, `piso`, `estrato`, `antiguedad`, ...) as `str` rather than typing them — those are parsed by the existing tolerant helpers in `seed_mapper.py` (`parse_parking`, `parse_bathrooms`, etc.), which handle values like "Sin especificar"; typing them here would break that reuse. `lat`/`lon` are `float` (no messy variants, needed as float for `PointToResolve` anyway).
- **`BulkCreatePropertiesUseCase.execute()`**: rebuilt the batch loop to consume `iter_csv_rows` (already-resolved dicts) instead of raw split lines, batching at 2500 rows with a slice-and-carry-remainder pattern plus a final flush after the stream ends (same shape as `chunk_file`'s trailing-byte flush).
- **`_process_batch(batch)`** implemented: assigns each row a correlation id (`str(index)` within the batch — plain index, not a real UUID, since `PointToResolve.id` is just `str`), builds `PointToResolve` per row (skipping/erroring rows with unparseable lat/lon before calling catalog), calls `catalog.get_locations_bulk` once for the whole batch, then merges `ResolvedPoint.location` back into each row by id — iterating over the *response* (not the input batch) so unresolved rows (`location is None`) are collected as errors instead of silently passing through without `neighborhood_id`/`city_id`/`country_id`.

## Open questions
- **Users bulk resolve direction is backwards for this use case.** What got built (`AccountReaderPort.get_accounts_bulk`, committed separately in `eda7114`) takes `account_ids: list[uuid.UUID]` and returns `(account_id, email)` — but the CSV has `email` and the pipeline needs `account_id` (owner_id resolution). Needs a signature flip (`list[str]` of emails in, `account_id` out) before this can actually be used here — explicitly deferred to "point 4" of this session's plan, not started.
- What happens to a CSV row whose email doesn't match any account (create placeholder? reject the row?) — same open question as the original `2026-07-16-bulk-create-owner-id-resolution.md` source, still unresolved.
- Dead code left in `execute()`: the old per-row `asyncio.gather` + `Semaphore` + `_enrich_location` flow (referencing undefined `records`/`sem`) is still present below the new batch loop, not yet removed or reconciled with `_process_batch`'s output.
- No batch-size limit on catalog's `get_location_by_points` server side (from the previous session's source) still applies — 2500 rows per call was chosen properties-service-side, not validated against catalog's query-size tolerance.
