# Revisión de catalog-service (solo lectura)

## Resumen

Revisé catalog-service por rebanadas verticales (ruta → caso de uso → repositorio/SQL → schema, más el consumidor del front de barrios admin) cotejando contra `domain-invariants.md`, `backend.md` y `frontend.md`. El servicio está en buena forma: `require_admin` está a nivel de router en todo `/admin`, el patrón sync/async (`run_in_threadpool(partial(...))`) es correcto en todos los casos de uso, las escrituras hacen `rollback()` + `translate_db_error`, el área se calcula sobre la geometría original como `geography`, el bbox de vecinos se valida en el schema y `count_all`/`get_coverage` respetan la regla de filtros compartidos.

El hallazgo nuevo y confirmado es **un bug de degradación de cache en `ResolveNeighborhoodUseCase`**: a diferencia del resto del servicio, sus llamadas a Redis no están envueltas, así que una caída de Redis rompe el request en vez de degradar a la DB. Es la causa de 2 de los 7 tests rojos de catalog-service en `audit-report.txt`. Los otros 5 rojos son tests desactualizados (no un bug de producción). Ambos grupos ya figuran en `open-items.md`, pero el backlog los deja como sospecha ("puede ser un bug real"); esta revisión confirma el diagnóstico de cada uno y aporta el escenario de falla y el fix concreto.

Entradas obligatorias leídas: `audit-report.txt` (sección catalog-service: ruff + 7 pytest rojos) y los pendientes de catalog en `docs/wiki/_shared/open-items.md`. Los ítems ya listados ahí (UpdateCountry que no invalida la lista pública, bulk síncrono, GET admin faltantes, falta de tests de integración, orígenes CORS fijos) **no** se reportan de nuevo salvo donde esta revisión agrega información.

## Bugs

### [Bug · alta] `ResolveNeighborhoodUseCase` no degrada ante Redis caído: el request falla
- **Dónde:** `backend/catalog-service/src/app/services/geo_resolution/use_cases/resolve_neighborhood.py:59` (`self.cache.get_json`) y `:75` (`self.cache.set_json`), dentro de `_resolve_coordinates`.
- **Escenario:** Un cliente llama `GET /geo-resolution/resolve-neighborhood?query=Calle+72&locality_id=...` con Redis caído. **Entrada:** request válido, Redis no responde. **Resultado incorrecto:** `self.cache.get_json(...)` (o `set_json`) propaga la excepción (`Exception("Redis down")`) y el caso de uso explota antes de devolver el barrio; el handler la convierte en 500. **Resultado esperado:** la excepción de cache se traga, se cae a geocodificar contra el gateway y leer de la DB, y el request responde 200 con el barrio resuelto.
- **Por qué pasa:** El adapter de cache (`services/shared/adapters/redis_cache_adapter.py`) delega directo al cliente de Redis y propaga cualquier error; no absorbe fallos. El invariante "Redis es opcional … toda operación de cache va envuelta para degradar en silencio" se cumple en los vecinos de este mismo servicio —`GetNeighborhoodsByLocalityUseCase` (`geo_catalog/use_cases/get_neighborhoods_by_locality.py:29-34,55-61`) y `GetNeighborhoodByIdUseCase` (`geo_catalog/use_cases/get_neighborhood_by_id.py:27-33,46-55`) envuelven cada `get_json`/`set_json` en `try/except Exception: pass`— pero `ResolveNeighborhoodUseCase` dejó ambas llamadas sin envolver. Es la raíz confirmada de los 2 tests rojos `test_survives_cache_get_failure_falls_back_to_geocoding` y `test_survives_cache_set_failure_still_returns_result` (`tests/unit/services/GeoResolution/use_cases/test_resolve_neighborhood.py:105,119`), que inyectan `side_effect = Exception("Redis down")` y esperan que el UC sobreviva.
- **Propuesta:** Envolver la lectura y la escritura de cache en `_resolve_coordinates` con el mismo `try/except Exception: pass` que ya usan los casos de uso de `geo_catalog`. En el `get_json`: si falla, tratar como miss (seguir a geocodificar). En el `set_json`: si falla, ignorar y devolver las coordenadas igual. Alternativa más limpia a futuro: mover la degradación al propio adapter para no repetir el patrón en cada UC — pero eso cambia el contrato del `CachePort` para todo el servicio y hay que decidirlo aparte; el fix mínimo y consistente con el código actual es envolver en el UC.
- **Test sugerido:** Ya existen y hoy están rojos: los dos tests citados arriba pasarían con el fix. Vale además un tercero que verifique que, con `get_json` fallando, igual se llama a `forward_geocode` y a `get_neighborhood_by_coordinates`.
- **Confianza:** alta

### [Bug · media] `ResolvePoiUseCase`: operaciones de cache fuera del `try` rompen la tarea de POIs si Redis cae
- **Dónde:** `backend/catalog-service/src/app/services/geo_resolution/use_cases/resolve_poi.py:63` (`self.cache_client.get`) y `:69-71` (`set_nx`), antes del bloque `try/except/finally` que empieza en `:76`.
- **Escenario:** `resolve-neighborhood` y `by-coordinates` lanzan `poi_uc.execute(...)` como `BackgroundTasks` (`api/routes/geo_resolution.py:44-50,66-72`). **Entrada:** resolución exitosa de un punto con Redis caído. **Resultado incorrecto:** `await self.cache_client.get(key=cache_key)` (línea 63) o el `set_nx` del lock (69-71) lanzan antes de entrar al `try`, la excepción no la atrapa nadie dentro del UC y sube como error no manejado de la tarea de background (queda en logs del server como tarea fallida); los POIs no se pueblan. **Resultado esperado:** como todo el camino de POIs es best-effort y fire-and-forget, un Redis caído debería saltearse el cache/lock y, o bien seguir contra la DB/Overpass, o abortar silenciosamente sin propagar.
- **Por qué pasa:** El `try/except Exception` que haría degradar está más abajo (`:76`); las dos primeras operaciones de cache quedaron afuera. No rompe el request del usuario (ya respondió), pero contradice el invariante de cache opcional para esta ruta. Severidad media y no alta porque es una tarea de background: el usuario no ve el 500, solo se pierde el poblado de POIs de esa celda.
- **Propuesta:** Envolver el `get` inicial y el `set_nx` del lock en manejo best-effort (o ampliar el `try` para que cubra desde la línea 63), tratando el fallo de Redis como "sin cache / sin lock" en vez de dejar propagar. Cuidar el `finally` que borra el lock: si no se adquirió por Redis caído, el `delete` del lock también debe tolerar el fallo.
- **Test sugerido:** Unit del UC con `cache_client.get` y `cache_client.set_nx` lanzando `Exception`; afirmar que `execute(...)` no propaga y que, según la decisión, o se intenta `_fetch_and_persist` o se retorna sin error.
- **Confianza:** media

### [Bug · media] `ResolveIsochroneUseCase` no degrada ante Redis caído
- **Dónde:** `backend/catalog-service/src/app/services/geo_resolution/use_cases/resolve_isochrone.py:37` (`self.cache.get_json`) y `:94-98` (`self.cache.set_json`).
- **Escenario:** `POST /geo-resolution/reachable-pois` con Redis caído. **Entrada:** `IsochroneRequest` válido. **Resultado incorrecto:** `await self.cache.get_json(...)` propaga la excepción de Redis y el endpoint responde 500, aunque ORS y la query de POIs estén sanos. **Resultado esperado:** cache miss silencioso → calcular isócronas vía ORS + agrupar POIs → responder 200 (y el `set_json` final también debe tragar el fallo).
- **Por qué pasa:** Mismo patrón que `resolve_neighborhood`: las llamadas a cache no están envueltas. Aquí no hay test rojo que lo delate porque la suite de isócronas no cubre el caso de Redis caído, pero el invariante aplica igual. Lo marco media (no alta) porque no está confirmado por un test en rojo; el escenario sí es concreto y deducible del código.
- **Propuesta:** Envolver `get_json` (tratar error como miss) y `set_json` (ignorar error) en `try/except Exception`, igual que en `geo_catalog`.
- **Test sugerido:** Unit con `cache.get_json.side_effect = Exception(...)`: afirmar que se llama a `gateway.get_isochrones` y que se devuelve el resultado calculado.
- **Confianza:** media

## Mejoras

### [Mejora · media] 5 tests rojos de `GeoCatalog/test_get_neighborhoods_by_locality.py` están desactualizados respecto de la firma actual del UC
- **Dónde:** `backend/catalog-service/tests/unit/services/GeoCatalog/use_cases/test_get_neighborhoods_by_locality.py` (todo el archivo) vs `src/app/services/geo_catalog/use_cases/get_neighborhoods_by_locality.py`.
- **Diagnóstico (causa de 5 de los 7 rojos):** El UC evolucionó a **multi-localidad**: `execute(self, locality_ids: list[uuid.UUID]) -> NeighborhoodsByLocalityResponse` y llama a `uow.neighborhoods.get_active_by_locality_ids` (plural), que es lo que declara el port (`geo_catalog/ports/neighborhood_repository.py:8`) y lo que implementa el repo (`geo_catalog/adapters/sql_neighborhood_repository.py:16`). Los tests, en cambio, llaman `execute(locality_id=LOCALITY_ID)` (singular), mockean `uow.neighborhoods.get_active_by_locality_id` (singular, método que ya no existe) y comparan contra una `list[NeighborhoodListItem]` cuando el UC hoy devuelve un `NeighborhoodsByLocalityResponse` (dict por `locality_id`). Son tests que quedaron atrás tras el refactor, **no** un bug de producción: el código, el port y el adapter son coherentes entre sí.
- **Beneficio:** Actualizar los tests devuelve la suite a verde y vuelve a cubrir el camino cache-aside multi-localidad real (hit por una localidad y miss por otra, degradación de Redis, agregación por `locality_id`), que hoy no se verifica. Mientras sigan rojos enmascaran regresiones futuras en este UC.
- **Nota:** `open-items.md` ya registra "7 tests unitarios rojos en catalog-service" como pendiente; esto no lo re-reporta como hallazgo nuevo, aporta la causa raíz separando los 5 (tests viejos) de los 2 (bug de cache real, arriba).
- **Confianza:** alta

### [Mejora · baja] `useAdminNeighborhoods.fetchPage` no descarta respuestas fuera de orden
- **Dónde:** `frontend/src/composables/admin/useAdminNeighborhoods.ts:31-54` (`fetchPage`; la asignación sin guard `page.value = data` está en `:46`).
- **Diagnóstico / riesgo:** Las otras dos composables de la misma rebanada protegen contra respuestas tardías con un token `latestRequest` (`useNeighborhoodDetail.ts:11,14,26` y `useNeighborhoodNeighbors.ts:11,14,24`), siguiendo el invariante del front "una respuesta vieja nunca pisa a una nueva". `fetchPage` no lo hace: asigna `page.value = data` sin comparar contra una petición más reciente. En la práctica el riesgo es acotado —el cambio de filtros entra por `watch(urlFilters, load)` y siempre resetea a página 1, y las flechas de paginación se deshabilitan con `hasPrev/hasNext`— pero una secuencia rápida (cambiar filtro mientras una página anterior sigue en vuelo, o doble clic en "siguiente" con red lenta) podría dejar pintada la respuesta vieja. No pude construir un escenario de falla determinístico con el código actual, por eso va como mejora de baja confianza y no como bug.
- **Beneficio:** Alinear las tres composables con el mismo guard elimina la clase de bug de carrera por completo y hace el patrón uniforme.
- **Propuesta:** Agregar el mismo `let latestRequest = 0; const request = ++latestRequest;` y aplicar `page.value`/`loading`/`error` solo si `request === latestRequest`.
- **Confianza:** baja

## Revisado sin hallazgos

- **`require_admin` en todo `/admin`.** El router de admin se monta con `dependencies=[Depends(require_admin)]` a nivel de router (`api/routes/admin/__init__.py:7`), que cubre countries, admin_divisions, localities y neighborhoods, incluidos los bulk. `require_admin` valida el rol contra `settings.ADMIN_ROLE` sobre el principal del JWT (`api/deps/auth.py`). Invariante cumplido.
- **Identidad desde el JWT.** `get_current_principal` (`api/deps/auth.py`) valida el token y arma el `Principal`; los casos de uso no leen tokens.
- **Sync/async con `run_in_threadpool(partial(...))`.** Verificado en create/update de country/neighborhood, bulk_create, bulk_enrich, enrich_geometry, list_all, list_geometries, resolve_neighborhood, resolve_location_by_coordinates, bulk_resolve, resolve_poi y resolve_isochrone: todos los repos síncronos se llaman con `partial`. No encontré `await` directo sobre un repo ni `run_in_threadpool(repo.metodo(...))` sin `partial`.
- **Rollback + `translate_db_error` en escrituras.** country create/update, neighborhood create/update, enrich_geometry y bulk_enrich hacen `rollback()` y relanzan vía `translate_db_error` en el camino de error. `bulk_create` hace rollback antes del fallback fila-por-fila y usa savepoints (`begin_nested`/`rollback_to_savepoint`) por fila.
- **`search_name` normalizado y recomputado.** `_normalize` (NFKD, sin combinantes, `lower()`, `strip()`) se aplica en create (`create.py`), en cada fila del bulk (`bulk_create.py:_to_neighborhood`) y en update solo cuando cambia `name` (`update.py:40-42`). El matching de bulk_enrich normaliza con la misma función. Coherente con el invariante.
- **Listado admin de barrios: filtros compartidos.** `get_all` y `count_all` comparten `_apply_filters` (`catalog_admin/adapters/sql_neighborhood_repository.py:46,70,76`); `get_coverage` reusa `_apply_filters` pero con `has_geometry` forzado a `None` vía `req.model_copy(update={"has_geometry": None})` (`:78-82`), exactamente la excepción que pide el invariante. `get_all` ordena por `(name, id)` → paginación estable.
- **Área como geography sobre la geometría original.** `get_detail` calcula `ST_Area(cast(geom, Geography))` sobre `Neighborhood.geom` original; la simplificación (`ST_SimplifyPreserveTopology`) solo se usa para el `ST_AsGeoJSON` de salida, no para el área (`:112-124`).
- **Validación del bbox de vecinos en el schema.** `ListNeighborhoodGeometriesRequest` (`catalog_admin/schemas/neighborhood.py:84-98`) valida rangos vía `Lon`/`Lat` (`ge/le`), `min < max` y lado ≤ `0.135°`. El front manda `bbox` repetido con `paramsSerializer: { indexes: null }` (`useNeighborhoodNeighbors.ts`), que coincide con lo que espera FastAPI.
- **Lecturas admin sin cache / públicas con cache y solo activos.** Los UCs admin (`list_all`, `get_detail`, `list_geometries`) van directo a la DB, sin cache. Los públicos de `geo_catalog` (`get_countries`, `get_neighborhoods_by_locality`, `get_neighborhood_by_id`) usan cache-aside y filtran `is_active == True` en el repo (`geo_catalog/adapters/sql_neighborhood_repository.py:22,37`). Invariante cumplido.
- **`AdminDivision` de un solo nivel.** Los UCs de admin_division (`create`/`update`) no tienen auto-referencia ni jerarquía recursiva.
- **Resolución por coordenadas: prefiltro H3 + segunda pasada.** `get_location_by_point` y `_match_points` (`geo_resolution/adapters/sql/georeferentiation_repository.py`) acotan por `h3_cells.any(cell)` + `ST_Contains`, y si la celda es fría barren todos los barrios con `geom` — el `ST_Contains` sigue decidiendo el barrio, correcto para punto-en-polígono. El bulk usa `unnest` + `LATERAL JOIN` (un `ST_Contains` por punto, sin N+1). Puntos fuera de todo barrio devuelven `None`/404 (`resolve_location_by_coordinates.py`). Las tareas de POIs se disparan como `BackgroundTasks` tras resolver (`api/routes/geo_resolution.py`).
- **POIs: cache-aside, lock y FetchZone.** `resolve_poi` chequea cache → lock `set_nx` con TTL → DB (`get_by_h3_index`) con frescura por `fetched_at + STALE_THRESHOLD_DAYS` → Overpass → persiste POIs + FetchZone + actualiza `h3_cells` → libera el lock en `finally`. (El borde de Redis caído está reportado como bug media arriba; la lógica de lock/stale en sí es correcta.)
- **Isócronas: ORS, agrupado por celda, cache condicional.** `resolve_isochrone` calcula celdas por isócrona, agrupa POIs en memoria por `h3_index`, acumula los perfiles sin isócrona como `error` y **solo cachea si no hubo errores** (`:93`), evitando congelar respuestas parciales. (El borde de Redis caído está reportado arriba.)
- **`H3_RESOLUTION` consistente.** Un único `settings.H3_RESOLUTION = 9` se usa para indexar y consultar (resolve, bulk, isócronas, enrich); no hay resoluciones mezcladas dentro del servicio.
- **Handlers de excepciones.** `register_exception_handlers` mapea los `code` de dominio a HTTP y, a diferencia de properties-service, **sí** incluye `exc.context` en el body (`api/handlers/exception_handlers.py:60-66`), así que los 409/422 con contexto viajan al cliente.
- **GeoJSON inválido en bulk_enrich y enrich_geometry.** El router captura `json.JSONDecodeError` → 422 (`api/routes/admin/neighborhoods.py`); `enrich_geometry` rechaza tipos que no sean `Polygon`/`MultiPolygon` con `NeighborhoodInvalidGeometryError` → 422.
- **Invalidación de cache en escrituras de barrio.** create/update/enrich_geometry refrescan `cache_key_neighborhood(id)` y borran `cache_key_neighborhoods(locality_id)`; bulk_create borra la lista de la localidad; bulk_enrich borra la clave de cada barrio tocado **más** la lista de la localidad (`bulk_enrich_geometries.py:97-101`). Cubre entidad + listas que la contienen.
- **Instancia axios del front.** `catalogApi` usa `withCredentials: true` (cookie de auth) y el interceptor de auth; los endpoints salen de `constants/catalogEndpoints.ts`. La vista admin de barrios respeta "la URL es la fuente de verdad": `watch(urlFilters, load, { immediate: true })` con `router.push({ query })` desde `onApplyFilters` (`AdminNeighborhoodsView.vue`).

## Fuera de alcance / ya en el backlog (no re-reportados)

Estos ya están en `open-items.md` (sección catalog-service) y los dejo anotados solo para trazabilidad; no son hallazgos nuevos de esta revisión:

- `UpdateCountryUseCase` refresca `cache_key_country(id)` pero no borra `cache_key_countries()` (la lista pública queda vieja hasta el TTL). Confirmado en `country/update.py:42-50` vs `country/create.py:48`. Ya documentado como pendiente.
- Bulk create/enrich de barrios son síncronos end-to-end (leen el archivo entero en el request). Ya documentado.
- Faltan los GET admin de localidades, divisiones y países (el panel no puede ver/reactivar lo inactivo). Ya documentado.
- Las queries admin de barrios (`_apply_filters`, `get_coverage`, `get_geometries`) no tienen tests de integración; `tests/integration/adapters` está vacío. Ya documentado.
- Orígenes CORS fijos en código. Ya documentado.
- `resolve-neighborhood` marcado para deprecación (duplica el SDK de geocoding del front). Ya documentado. El bug de cache de arriba aplica igual mientras el endpoint siga vivo.
