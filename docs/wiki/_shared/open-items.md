## Fase 5 — Diferenciadores

### Crítico — flujo de valor

- [ ] **Worker de properties que consume `price-predicted`.** Cablear el consumer que escucha el topic de [[analytics-service]] y llama `SetEstimatedPriceUseCase` con `principal=None` para poblar `ml_estimated_price`. Hoy `workers/` de properties está vacío y el path ML no tiene caller — es el flujo async properties↔analytics que [[architecture]] marca "en definición". Sin esto, el precio del AVM nunca llega al listing. Ver [[adr-estimated-price-dual-signal]], [[properties-service-admin]].
- [ ] **Desactivación de cuenta no propaga a los listings del usuario.** `DeactivateCurrentAccountUseCase` (`deactivate_current_account.py:20-42`) marca la cuenta `is_active=False` e invalida su cache, pero no notifica a nadie — los listings del usuario en [[properties-service]] quedan publicados y visibles en el feed aunque el dueño ya no esté activo. Falta: publicar un evento (ej. Kafka `account.deactivated {account_id}`) y un consumer en properties-service que marque `inactive` todos los listings de ese `owner_id`. Mismo patrón fire-and-forget que `price-predicted` (ítem anterior). Ver [[users-service]], [[properties-service-admin]].

### Impresiones, analytics de comportamiento y feed personalizado

- [ ] **Tracking de impresiones por listing.** Registrar cuántas veces fue visto cada listing (impression) y por quién (si está autenticado). Candidato a evento Kafka `listing.impressed` consumido por analytics-ms. Sin esto, el propietario no puede saber el alcance de su publicación. El enfoque (beacon de cliente → collector tonto → Kafka → consumer en analytics) está fijado en [[adr-impressions-beacon-pipeline]]. Ver [[properties-service]], [[analytics-service]].
- [ ] **Modelo de recomendación de promociones.** Con el historial de impresiones se puede entrenar un modelo que identifique qué listings promocionados tienen mayor probabilidad de conversión para cada perfil de usuario. Input: intereses del usuario + historial de views + features del listing. Ver [[analytics-service]], [[adr-estimated-price-dual-signal]].
- [ ] **Feed personalizado por comportamiento.** Hoy el feed filtra por preferencias declaradas (onboarding). Con tracking de comportamiento (qué vio, cuánto tiempo, si volvió) se puede alimentar un recomendador colaborativo o content-based que mejore el ranking. El bbox del mapa estilo Airbnb ya da señal de zona de interés implícita. Ver [[frontend-architecture]], [[analytics-service]].
- [ ] **Targeting de listings promocionados.** Cruzar perfil del usuario (barrios, tipo de propiedad) con historial de comportamiento para mostrar los promoted listings a las personas con mayor probabilidad de conversión — no al azar. Depende de los dos ítems anteriores.

### Producto — diferenciadores y gaps de mercado

- [ ] **Score de oportunidad de inversión inline en el feed.** Calcular `(precio_listado - precio_estimado) / precio_estimado` y exponerlo en `PropertyCardSchema` como campo numérico + badge visual en cada card. Diferenciador directo vs FincaRaíz/Metrocuadrado (sin AVM); supera a Cerouno (calculadora manual vs automático en cada card del feed). Depende del worker AVM → listing (`ml_estimated_price` poblado). Ver [[adr-estimated-price-dual-signal]], [[properties-service-search]].
- [ ] **Alertas de oportunidad de precio.** Notificación push/email cuando se lista una propiedad X% por debajo del precio estimado en la zona de interés del usuario. Alta conversión para perfiles de inversión — nadie en el mercado colombiano lo tiene automático. Requiere: AVM funcionando + sistema de notificaciones + preferencias de zona ya capturadas en onboarding. Ver [[adr-estimated-price-dual-signal]], [[users-service]].
- [x] **`POST /v1/geo-resolution/reachable-pois` en catalog-service (isócronas).** Implementado 2026-06-15. ORS → `polygon_to_cells(r9)` → `get_by_h3_cells` (1 query) → groupby en memoria → `list[ReachablePoisResult]`. Soporta múltiples perfiles en parallel gather. Ver [[catalog-service]], [[catalog-service-ors]], [[adr-isochrone-ors-h3]].
- [ ] **Búsqueda con lenguaje natural.** LLM con tool use que traduce una query en lenguaje natural a la estructura `preferences + filters` del endpoint `/v1/search/feed`. Cerouno ya la tiene → brecha competitiva activa. El endpoint de búsqueda ya soporta todos los parámetros necesarios; falta la capa de traducción. Ver [[properties-service-search]], [[frontend-architecture]].
- [ ] **Estrato socioeconómico en el modelo de propiedad.** Agregar campo `stratum` (1–6) a la tabla de propiedades. En Colombia el estrato predice precio, servicios públicos y entorno — feature de alto valor para el AVM y para filtros del feed. Habi lo expone en cada card; FincaRaíz y Metrocuadrado también lo tienen. Sin él, el AVM pierde una de las variables más predictivas del mercado colombiano. Ver [[properties-service-admin]], [[avm-training]].
- [ ] **Página pública de perfil del publicante.** Mostrar quién publicó una propiedad (no solo el dashboard interno para admin) implica una página de usuario navegable por terceros, no solo un id. Camino mínimo: link "ver más de este publicante" reusando `GET /properties/users/{user_id}` (ya existe, devuelve `list[PropertyCardSchema]`) en una vista de feed filtrada — sin perfil nuevo. Camino completo: perfil público real (avatar, bio, rating, contacto) requiere nuevos campos/UCs en users-service expuestos a terceros (hoy probablemente solo el propio usuario autenticado los puede ver) — mucho más alcance, necesario si el publicante va a ser un actor visible (mensajería, reputación). Decidir alcance antes de implementar. Ver [[properties-service-listing]], [[users-service]].
  - [ ] **Sub-tarea — paginación server-side offset/limit en `GET /v1/properties/users/{user_id}`.** Hoy el endpoint devuelve la lista completa sin paginar (`SqlPropertyRepository.get_public_user_properties`, sin `.offset()/.limit()`). Con datasets de prueba grandes (admin bulk) se nota; un agente real no tendría tantos listings, pero paginar es barato porque `owner_id` ya está indexado y `Property` tiene `created_at` (vía `AuditMixin`) para ordenar de forma estable. Tocar: router (`properties.py`) → use case (`get_public_user_properties.py`) → port (`property_repository.py`) → repo SQL, agregando `limit`/`offset` con defaults. En frontend, `PublicProfileView.vue` pasa de paginación local (`slice` sobre mock) a un composable real que pagina por offset con un cache simple por página (no necesita cursor-stack como `useFeed`, porque el offset es invertible). Pendiente: el dev lo va a implementar manualmente para practicar.

### Deuda geo / ML

- [ ] **Re-registrar AVM con `year_built` nullable.** `_make_raw_input_example()` en `trainer.py` usa `year_built: 2012` (int) → MLflow infiere `long required` → rechaza `null` en runtime antes del preprocessing. Fix: pasar `year_built: None` en el ejemplo y re-correr `final_train` + promover alias `production`. Workaround temporal: reemplazar `None` con `0` en `AVMModelAdapter` tras el `model_dump`. Ver [[analytics-service-mlflow]].
- [x] **Conciliar tag set de POIs.** `category_map.py` unifica 5 keys OSM, 15 categorías, 147 valores — idéntico al tag set del AVM. `extract_category()` reemplaza el mapper anterior. Cerrado 2026-06-11. Ver [[catalog-service-overpass]], [[adr-geospatial-feature-engineering]].
- [ ] **Evaluar self-host de Overpass.** La instancia pública `overpass-api.de` empezó a devolver 406 a requests sin `User-Agent` descriptivo (mitigado 2026-06-23 seteando `settings.OVERPASS_USER_AGENT`) y sigue devolviendo `ServerLoadError` (504) bajo carga — riesgo de disponibilidad fuera de nuestro control. Self-host requiere levantar un Overpass propio (similar al contenedor ORS ya en `infra/`) y subir/mantener actualizados los extractos `.pbf` (Colombia/Bogotá) al servicio. Pendiente decidir si vale el costo operativo vs. seguir absorbiendo los fallos del público con retries. Ver [[catalog-service-overpass]].
- [ ] **Resolución H3 al cablear feature store desde un MS (caveat, no bug).** Los servicios indexan en r9 (lookup espacial granular) y el AVM usa r6/r7/r8 (feature del vector; r9 mete ruido). Hoy NO rompe nada porque el modelo recomputa sus celdas desde `lat/lon` en inferencia y no consume las celdas de los MS. Cuando se conecte el feature store desde un MS al modelo, **recomputar la resolución del modelo, no reusar la celda r9 almacenada**. Decisión en [[adr-h3-resolution-per-use-case]]; documentado en [[glossary#h3]].
- [ ] **CI + promoción del training AVM.** Automatizar el run (orchestrator tipo Airflow) y formalizar la promoción del alias `production` (hoy manual). Ver [[avm-training]], [[adr-model-promotion-external-to-service]].

### properties-service — arquitectura interna

- [ ] **Refactor: `CreatePropertyUseCase` construye el ORM model `Property` directamente (`create_property.py:62`).** El UC debería pasar el schema de dominio al repo y que el repo haga el mapeo al ORM model — leak de hex arch detectado 2026-06-30. Ver [[properties-service-listing]].
- [ ] **IMPORTANTE — `POST /admin/properties/bulk` es síncrono end-to-end y puede timeoutear en el front.** `BulkCreatePropertiesUseCase.execute()` llama a `catalog-service` por cada fila (`_enrich_location`, semáforo de 50 concurrentes) antes de `bulk_insert`+`commit`, todo dentro del mismo request HTTP. El front (`propertiesApi`, `timeout: 8000`) tiene 8s — un CSV de más de un puñado de filas fácilmente supera ese timeout por la latencia acumulada de red hacia catalog-service, y el cliente reporta error aunque el proceso siga corriendo (y comiteando) del lado del servidor. Detectado 2026-07-16 al construir el modal de importación admin en el front. Refactor propuesto (patrón fire-and-forget con batch, visto funcionando en un proyecto hermano): el endpoint valida+parsea sync, crea un batch `pending`, devuelve `202 { batch_id }` de inmediato, procesa (enrich + bulk_insert + commit) en background, y expone un endpoint de status para polling desde el front. Gotcha a tener en cuenta: en FastAPI ≥0.106 las dependencias `yield` (UoW/sesión) se cierran antes de que corra el `BackgroundTask` — el worker de background necesita abrir su propia sesión, no reusar la inyectada por `Depends`. Rama creada para esto: `refactor/bulk-async-processing`, sin código todavía (2026-07-17).
  - **Update 2026-07-19**: la clase se movió a `workers/bulk_create_properties.py` y se reconstruyó el pipeline de lectura — ahora streamea el CSV desde MinIO en chunks (en vez de `file.read()` completo) y resuelve ubicación con una sola llamada bulk a catalog por batch de 2500 filas (`_process_batch`, reemplaza a `_enrich_location`). **No resuelve el riesgo de arriba todavía**: no hay confirmación de que la ruta HTTP invoque esto vía `BackgroundTasks` en vez de `await` inline — el nombre del módulo (`workers/`) sugiere la intención pero no está verificado. Además, `_process_batch` quedó **desconectado** del resto del pipeline (`row_to_item`/`build_models`/`bulk_insert`) — el código viejo de `_enrich_location`/`asyncio.gather` sigue en `execute()`, ahora roto (referencia variables indefinidas), no un fallback funcional. Ver [[properties-service-bulk-create-worker]], `docs/sources/properties-service/2026-07-19-bulk-create-worker-streaming-csv.md`.
  - [ ] **Diseño refinado (2026-07-17, sin implementar).** Tabla `bulk_jobs` por servicio (no compartible entre servicios — DBs separadas) con `job_type` enum discriminador — en catalog-service la misma tabla sirve para `bulk_create_neighborhoods` y `bulk_enrich_neighborhood_geometries` (ver ítem de catalog-service más abajo). Shape: `id` (uuid devuelto al caller), `job_type`, `status`, `total_rows`/`processed_count`/`success_count`/`error_count`, `created_by`, timestamps, `errors` (lista JSON por fila). Precedentes reusados en vez de inventar desde cero: shape de `kc_compensation_tasks` (users-service) y `property_image_upload_batches` (properties-service). Bulk es **solo create** — no hay verbo de "bulk update"; corregir un batch es delete-by-`bulk_job_id` + create nuevo (ver `Property.bulk_job_id` FK nullable más abajo), no un merge in-place. **Dedup: decidido NO hacer hash/idempotencia automática** — se evaluó y descartó (a) hash de fila completa como key sintética (rompe con cualquier edición legítima, en particular precio) y (b) excluir precio del hash + del `DO UPDATE` con heurística de detección de abuso a nivel de batch (juzgado sobre-ingeniería para la necesidad real). Reintentar con el mismo archivo sin usar la acción de redo puede duplicar — comportamiento esperado y documentado (tooltip en el front), no prevenido por el sistema. Mitigación real: `Property.bulk_job_id` (FK nullable) para trazabilidad + acción de "redo" que soft-borra (mismo patrón que `delete_property.py`, no hard delete) todas las properties de ese `bulk_job_id` y reprocesa como job nuevo con `retry_of_job_id` apuntando al original (el job fallido queda en el historial, no se pisa). El delete filtra server-side por `bulk_job_id`, no recibe lista de ids del front. **Simplificación grande**: el CSV se sube por presigned URL directo a MinIO (mismo patrón que `property_image_upload_batches` para fotos) en vez de proxyarse por el request (hoy `file.read()` sync en `admin.py`) — el endpoint bulk recibe la storage key, no bytes. Consecuencia: un reintento no resube nada, el background job relee el mismo objeto de storage — cero bandwidth en el reintento. Pendiente: TTL de retención del archivo en storage (para que un reintento no reuse una key vieja con datos stale indefinidamente), validación de content-type antes de emitir la presigned URL, expiración de la URL presigned misma. Ver [[adr-image-upload-presigned-batch]] (patrón de referencia), `docs/sources/properties-service/2026-07-17-bulk-async-redesign-presigned-retry.md`.
- [ ] **IMPORTANTE — bulk create le pone `owner_id` = el admin que ejecuta el import, no el dueño real.** `build_models(item=item, owner_id=principal.sub, created_by=principal.sub)` usa el mismo UUID (el admin logueado) para ambos campos — hoy todas las propiedades importadas en bloque quedan "de propiedad" del admin, apareciendo en su propio `GET /properties/me`. `created_by=principal.sub` está bien (es auditoría real: quién ejecutó la acción). `owner_id` está mal: debería resolverse contra una cuenta real del dueño, no hardcodearse al importador. Detectado 2026-07-16, mismo hallazgo que el ítem de arriba (mismo endpoint). Decisión tomada: resolver `owner_id` por **email** — ya existe como campo único+indexado en `Account` (users-service), sin necesitar migración ni nuevo dato de identidad (se descartó cédula: no existe ese campo en el sistema hoy, agregarlo implica migración + decidir qué hacer si no matchea). El CSV de bulk necesitaría una columna de email por fila; si no matchea ninguna cuenta, a definir (¿crear cuenta placeholder? ¿rechazar la fila?) — email es solo el punto de partida, en onboarding se podrían pedir más datos de identidad más adelante. Bonus: desbloquea poder atribuir imports de demo a varias cuentas fabricadas en vez de que todo quede bajo un mega-dueño (un solo admin con cientos de propiedades no se ve realista en un demo). Trazabilidad del batch: no hace falta un mecanismo aparte — la entidad de batch que ya se necesita para el refactor async de arriba (`202 + batch_id`) puede servir también para rastrear qué `property_id`s salieron de qué import. Ver `seed_mapper.py` (`build_models`), `bulk_create_properties.py`, `Account` en users-service (`models/account.py` — solo `account_id`/`email` como identificadores únicos hoy).

Fix de una línea, mismo patrón que ya usa `CreateCountryUseCase`. Detectado en la auditoría de admin endpoints 2026-07-17 (ver sección de properties-service arriba, mismo concern).

- [ ] **IMPORTANTE — falta un endpoint bulk de geo-resolución; el bulk create de properties-service hace N llamadas individuales.** `BulkCreatePropertiesUseCase._enrich_location` (properties-service) llama `GET /v1/geo-resolution/by-coordinates` **una vez por fila** del CSV — el `Semaphore(50)` acota la concurrencia pero no el total de llamadas: un CSV de 5000 filas son 5000 requests HTTP a catalog-service, cada uno disparando su propia query PostGIS (`ST_Contains`) por separado. Agravante: `CatalogClient.get_location_info()` abre un `httpx.AsyncClient()` nuevo por llamada, sin reuso de conexión. Detectado 2026-07-16, directamente acoplado al refactor async de `bulk_create_properties` (ver ítems de properties-service arriba) — con ese refactor el timeout del cliente deja de ser el síntoma visible, pero la carga real sobre catalog-service no desaparece, solo se vuelve invisible (background). **Update 2026-07-18 — lado catalog-service implementado**: `POST /v1/geo-resolution/by-coordinates/bulk` existe (`BulkResolveLocationsByCoordinatesUseCase` + `get_location_by_points`, resuelve el batch con `unnest(...)` + `LEFT JOIN LATERAL` — una sola query PostGIS en vez de N, con fallback de segunda pasada solo para los puntos que no matchean por el prefiltro h3). **Update 2026-07-19 — la otra mitad ya se conectó, parcialmente**: `CatalogClient.get_locations_bulk` + `_process_batch` (properties-service) ya llaman al endpoint bulk una vez por batch de 2500 filas, en vez de N llamadas individuales. Pendiente: `_process_batch` todavía no está conectado al resto del pipeline de inserción (ver ítem de arriba) — el ahorro de N llamadas ya existe en el código, pero el flujo end-to-end no inserta properties todavía. Ver [[properties-service-catalog]], [[properties-service-bulk-create-worker]], `docs/sources/properties-service/2026-07-19-bulk-create-worker-streaming-csv.md`.

### Infra compartida entre servicios

- [ ] **Centralizar los clientes de Redis y MinIO en una librería interna compartida (single source of truth).** Hoy cada MS copia su propio stack: el de cache Redis (`integrations/cache/redis/cache.py` + `services/shared/adapters/redis_cache_adapter.py` + `services/shared/ports/cache.py` + `core/exceptions/cache.py`) existe por triplicado en catalog, properties y users; el de MinIO (`integrations/storage/minio/storage.py` + adapter + port + exceptions) por duplicado en properties y users. Las copias **ya divergieron** (verificado 2026-06-12, ningún hash coincide): el port de cache de users tiene los 7 métodos base, catalog agrega `set_nx`, properties agrega `mget`/`mget_json`/`mset`/`mset_json` y `delete` multi-key; en storage divergieron hasta funcionalmente — properties expone presigned PUT URLs y users hace `upload_file` server-side. Un bugfix o mejora en una copia no llega a las demás. Propuesta: paquete interno del monorepo (p. ej. `backend/_lib/`, instalable por path con uv) que centralice el cliente Redis (superset de métodos), el cliente MinIO y las excepciones base; cada servicio conserva su port de dominio — el hexagonal se respeta porque lo compartido es el adapter/cliente de infra, no el contrato del dominio. Trade-off: acoplamiento por shared lib (un cambio breaking obliga a actualizar N servicios en lockstep) vs el drift actual de 3+2 copias. **Decisión mapeada en [[adr-shared-infra-lib]] (2026-06-12)**: uv workspace, ports se quedan en cada servicio, scope infra-only; el coste principal es el ajuste de Dockerfiles/build context. Ver [[architecture]], [[adr-cache-optional-layer]]. **Extensión (2026-06-20)**: el mismo problema aplica a las *cache key conventions*, no solo al cliente. `DeletePropertyUseCase`/`UpdatePropertyUseCase` en properties-service necesitan invalidar `geo:reachable:property:{property_id}` (key de catalog-service, ver `get_isochrone_key`) al borrar/mover una propiedad — viable sin llamada cross-service porque Redis es una instancia única compartida (mismo `REDIS_URL` en `.env`), pero hoy properties-service tendría que hardcodear el formato de una key que no le pertenece. Si el paquete compartido centraliza también los builders de cache key (no solo el cliente), este caso se resuelve gratis.

- [ ] **Validar redundancia del `try/except Exception: pass` de cache-aside en los tres servicios.** El ADR [[adr-cache-optional-layer]] documenta ese wrapper en los use cases como el patrón correcto para degradar a DB si Redis falla. En catalog-service se verificó (2026-06-20) que es redundante: `CacheClient.get_json`/`set_json` (`integrations/cache/redis/cache.py`) ya atrapan la excepción internamente y devuelven `None`/`False`, por lo que el wrapper en `ResolveNeighborhoodUseCase` y `ResolvePoiUseCase` no hacía nada — se quitó en ambos. Falta confirmar si las copias de `CacheClient` en properties-service y users-service (ya divergidas, ítem anterior) también atrapan internamente o si ahí el wrapper en el use case sigue siendo necesario porque el cliente propaga la excepción. Si las tres copias atrapan igual, el ADR debería aclarar que el wrapper en el use case es opcional/redundante, no parte del contrato. **Instancias concretas en properties-service pendientes de este veredicto** (auditoría de admin endpoints 2026-07-17): `moderation/set_status.py:54-64`, `moderation/verify.py:50-57`, `promotions/create.py:67-77`, `promotions/delete.py:40-50` — las cuatro comparten el mismo shape de `try/except Exception: pass` alrededor de la invalidación. Resolver la pregunta de redundancia primero (15 min de investigación) y aplicar el mismo veredicto a las cuatro de una — no una por una. Ver [[adr-cache-optional-layer]], [[catalog-service]].
- [x] **Cache-aside para `reachable-pois` con check pre-ORS.** Implementado 2026-06-20. `ResolveIsochroneUseCase.execute()` chequea `cache.get_json` con `get_isochrone_key(property_id=...)` si viene `property_id`, o con el h3 cell del punto (`h3.latlng_to_cell(lat, lon, settings.H3_RESOLUTION)`, no los cells del polígono de la isocrona) si no, antes de llamar `gateway.get_isochrones`. Es todo-o-nada por request porque ORS siempre devuelve los 3 profiles fijos en una sola llamada (`asyncio.gather` en `ors/routing.py`) — no hay cache parcial por perfil. Cachea la response completa (isocrona + POIs) solo si ningún profile dio error, TTL `settings.CACHE_TTL_ISOCHRONE_SECONDS` (1h). Pendiente: invalidación cruzada cuando se actualiza una propiedad (sin reverse index) — ver ítem `geo:reachable:property:{property_id}` arriba. Ver [[catalog-service-ors]], [[adr-isochrone-ors-h3]].

### properties-service — seguridad del feed

- [ ] **Rate limiting en `/search/feed`.** Sin esto el corte de `FEED_MAX_RESULTS` es trivial — N sesiones paralelas cada una llega a 300 orgánicos. Implementar límite por IP y/o por usuario a nivel de API gateway (nginx, Traefik) o middleware FastAPI + Redis. Ver [[properties-service-search]], [[adr-feed-opaque-cursor]].
- [ ] **Cursor firmado (HMAC).** El cursor actual es opaco pero no autenticado: alguien puede decodear el base64, manipular `created_at` para saltar a cualquier punto del dataset, y re-encodear. Un HMAC con secret server-side previene la manipulación sin cambiar el contrato público. Fix de mayor impacto/menor coste si el catálogo tiene valor real. Ver [[adr-feed-opaque-cursor]].
- [ ] **TTL del cursor.** Un cursor válido hoy lo es para siempre. Embeber una expiración (ej. 24 h) en el payload del cursor y validarla en `decode_cursor` fuerza re-inicio del flujo de paginación y reduce la ventana de scraping sostenido. Ver [[adr-feed-opaque-cursor]].

### properties-service — consistencia de cache en admin writes

Auditoría de endpoints admin 2026-07-17 (motivada por la revisión de bulk create) — se revisaron todos los routers admin de los 4 servicios. `users-service` y `analytics-service` no tienen endpoints admin, nada que auditar ahí. `require_admin` está bien implementado en catalog y properties, sin huecos de autorización. Aparecieron los siguientes bugs de cache, agrupados porque son el mismo concern y candidatos a una sola rama chica (`fix/admin-cache-consistency`).

- [ ] **IMPORTANTE — `ListPromotionsByPropertyUseCase` lee/escribe la cache key del detalle público con el schema equivocado.** `promotions/list_by_property.py:19-51` usa `cache_property(property_id)` — la key canónica de `PropertyDetailSchema`, poblada por `GetPropertyUseCase` (público) y `GetPropertyDetailAdminUseCase` — pero la trata como `PropertyCardSchema`. Dos efectos: (1) si lee un cache warm de detail, `is_promoted` siempre da `False` (el campo no existe en ese shape) → falso `PromotionNotFoundError` (404) aunque la propiedad esté promocionada; (2) si escribe primero, deja un payload shape-card (le faltan `condition`, `verification_status`) bajo la key de detail — la próxima lectura del detalle público de esa propiedad falla `model_validate` (silenciado por `except: pass`) y cae a DB siempre, cache roto para esa propiedad hasta que algo la reescriba bien. No es solo un bug admin — degrada tráfico público. Fix acotado a un archivo: este UC no necesita `cache_property` en absoluto, puede resolver `is_promoted` directo contra la promoción activa que ya está consultando.
- [ ] **`set_status.py` no invalida el cache de ads del feed.** `moderation/set_status.py:54-64` invalida `cache_property`, `client_properties`, `map_h3_cell`, `public_user_properties_pattern` al cambiar el status de una propiedad, pero nunca `feed_ads_global()`/`feed_ads_by_city()` (`search/helpers/feed/ads.py`, TTL 1h). Si un moderador saca de `active` una propiedad promocionada, sigue apareciendo como ad pago en el feed público hasta que expire el TTL. Mismo patrón (stale read after admin write) que la invalidación de countries en catalog-service (ver abajo).
- [ ] **`GET /admin/promotions` sin paginar.** `promotions/list_all.py:16-43` (repo `sql_promotion_repository.py:27-29`, `SELECT ... WHERE is_active` sin límite) — a diferencia de `GET /admin/properties`, que sí pagina con `page_size` acotado ≤100 (`admin_schemas.py:22-27`). Con volumen de promociones creciendo, respuesta de tabla completa + cache entry de `feed_ads_global` sin cota. Copiar el patrón de paginación ya existente en properties.
- [ ] **`SetEstimatedPriceUseCase` no invalida cache tras el write.** `estimated_price/set_estimated_price.py:18-38` — a diferencia de todo el resto de writes admin en este router, no hace ningún `cache.delete` tras comitear `admin_estimated_price`/`ml_estimated_price`. Hoy sin impacto visible (esos campos no están expuestos en `PropertyDetailSchema`/`PropertyCardSchema` todavía), pero va a empezar a servir precios stale el día que se expongan. Nota aparte: la rama `principal=None` (líneas 26-32) es código muerto hoy — el único caller es el router admin, que siempre inyecta un `Principal` requerido vía `require_admin`; confirmar si hay un caller interno/ML planeado antes de asumir que ese path está wireado y autorizado.

### properties-service — deuda pequeña

- [ ] **`PropertyImage.id` es un UUID random sin relación con el uuid de su storage key.** El flujo presigned genera dos UUIDs independientes por imagen: uno para la key (`{property_id}/{uuid}`, `request_presigned_urls.py:49`) y otro para el `id` del row en confirm (`default_factory=uuid.uuid4` del modelo, `confirm_image_uploads.py:88-95` no reusa el de la key). No es un bug — el flujo funciona — pero confunde: para ir del `id` de una fila a su objeto en storage hay que parsear el string `url`, no hay relación directa. A diferencia de POIs (`external_id`+`source` separados del `id` interno, correcto ahí porque ese id lo asigna OSM, un sistema externo), acá los dos UUIDs los genera el propio servicio en dos pasos del mismo flujo — no hay una segunda identidad externa que preservar. Propuesta: que el `uuid.uuid4()` generado al pedir la key sea el mismo que termina como `PropertyImage.id`, en vez de generar uno nuevo en confirm. Bonus: `url` (`f"{base_url}/{bucket}/{property_id}/{id}"`) pasaría a ser derivable en vez de necesitar guardarse — evita filas con `url` stale si `base_url`/bucket cambian (ej. migración de CDN). Detectado 2026-07-17 en discusión de diseño. Ver `request_presigned_urls.py`, `confirm_image_uploads.py`, [[adr-image-upload-presigned-batch]].
- [ ] **El worker no cierra el `BulkJob`.** `BulkCreatePropertiesUseCase.execute()` (worker) procesa y devuelve un `BulkCreatePropertiesResult`, pero nunca escribe de vuelta el `BulkJob` — no setea `status`, no persiste `errors`, no marca `confirmed_at`. El front que lee el job siempre ve `pending` + `errors=[]`, pase lo que pase; toda la razón de ser del modelo (status + errores para el front) queda desconectada. `BulkJobRepository` (port) solo expone `add`/`get_by_id` — falta un método de write-back (p. ej. `mark_finished(job_id, status, errors)`) y decidir la semántica de `failed` (¿`inserted == 0`? ¿solo si explota todo el batch?). `confirmed_at` está definido en el modelo y nunca se setea — semántica frente a `status` sin decidir. Detectado 2026-07-22. Ver [[properties-service-bulk-create-worker]], `docs/sources/properties-service/2026-07-22-bulk-create-properties-refactor.md`.

### frontend — deuda pequeña

- [ ] **Error/loading states en FeedView y MapView.** Ambas vistas carecen de skeleton de carga y de manejo de errores visibles. Sin esto, cualquier fallo de red en demo es invisible para el usuario y difícil de diagnosticar. Ver [[frontend-architecture]].
- [ ] **`checkAuth` siempre loguea 401 en consola para usuarios no autenticados.** El catch no filtra el 401 esperado — aparece como error visual en devtools aunque el flujo es correcto. Fix: `if (axios.isAxiosError(error) && error.response?.status !== 401)` antes de loguear. Natural hacerlo junto con la centralización del axios instance. Ver `stores/auth.ts:87`. **Update 2026-06-12**: el catch de `checkAuth` ya es silencioso ([auth.ts:87-93](frontend/src/stores/auth.ts#L87-L93)) pero el 401 **sigue apareciendo** en consola — es el log nativo de red del navegador (request XHR fallido), no suprimible desde JS. Cerrarlo de verdad implica evitar el request especulativo (p. ej. solo llamar `checkAuth` si hay señal de sesión previa) o aceptar el log como ruido conocido.

### Observabilidad y telemetría

Los tres pilares están ausentes hoy. Sin los tres juntos es imposible diagnosticar degradación en producción: los logs dicen *qué* falló, las métricas dicen *cuándo* empezó, las trazas dicen *dónde exactamente*.

#### Pilar 1 — Logs
- [ ] **Logging estructurado uniforme.** Hoy cada MS configura su propio logger con distintos formatos. Unificar en JSON con campos fijos (`service`, `trace_id`, `level`, `message`) para poder agregar en una sola vista (Loki, CloudWatch Logs, etc.). El `correlation_id` middleware de properties-service es un buen punto de partida.

#### Pilar 2 — Métricas
- [ ] **Métricas de infraestructura por MS (Prometheus/Grafana).** Exponer métricas clave: requests/s, p95 latencia, errores por endpoint, hit rate del cache Redis. Sin esto no hay forma de detectar degradación antes de que el usuario la reporte.
- [ ] **Métricas del AVM.** Latencia de inferencia, tasa de errores `PREDICTION_FAILED`, distribución de precios predichos. Permite detectar drift del modelo sin auditoría manual. Ver [[analytics-service]], [[avm-training]].
- [ ] **Métricas de negocio.** Tamaño del feed devuelto, tasa de listings sin impresiones (supply invisible), CTR de promoted listings. Distintas de las métricas de infra — miden salud del producto, no del sistema.

#### Pilar 3 — Trazas
- [ ] **Trazas distribuidas (OpenTelemetry).** Un request del feed puede tocar gateway → properties-service → catalog-service sin forma de correlacionar latencias hoy. Stack: `opentelemetry-sdk` + exportador a Jaeger o Tempo. Expandir el `correlation_id` existente a W3C TraceContext para propagación automática entre MSs. Ver [[architecture]].

### analytics-service — gaps funcionales

- [ ] **Kafka worker no levantado en startup.** `runner.py` del consumer existe pero no se llama desde `main.py` — el pipeline batch (listings → predicciones) está off by default. - [ ] **Promotions domain sin cache invalidation efectiva.** Los UCs `create.py` y `delete.py` de promotions tienen `except Exception: pass` en las operaciones de cache — las invalidaciones no se ejecutan si Redis tiene un error transitorio. Fix: separar la lógica de invalidación del manejo de errores de cache. Ver [[properties-service-admin]].
